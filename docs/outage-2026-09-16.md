# September 16 availability recovery

The public homepage timed out while `/healthz` continued returning 200. Database
activity included enrichment scans running over six minutes and collection
aggregations running over ten minutes against roughly 18.5 million items.
The public page cache expired every 60 seconds with no stale fallback or
coalescing of concurrent renders.

Recovery changes:

- Paused the BullMQ enrichment queue and cancelled its active database scans.
- Set PostgreSQL `plan_cache_mode = force_custom_plan` with `ALTER SYSTEM` and
  reloaded configuration, avoiding generic plans for parameterized optional filters.
  This can be reverted with `ALTER SYSTEM RESET plan_cache_mode` and
  `SELECT pg_reload_conf()`; no restart is required.
- Built `items_first_seen_idx` concurrently in production before deploying its
  idempotent migration. The rolling-day count used the index in 457 ms.
- Bounded enrichment candidates per collection before ranking. Production
  EXPLAIN ANALYZE of candidate selection completed in 240 ms.
- Added stale public HTML fallback for at least one hour and one concurrent
  refresh per page per process. Signed-in requests still bypass this cache.

The enrichment queue must be resumed after the fixed deployment becomes healthy.
Exact collection counts and tag aggregations still scale with collection size;
caching reduces their impact but does not replace precomputed aggregates.
